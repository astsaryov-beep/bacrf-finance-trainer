# Правила разработки и восстановления контекста

Этот документ обязателен для любого человека или ИИ-агента, который меняет тренажёр **«Финансовые рынки и институты»**.

## 1. Начало ЛЮБОГО рабочего сеанса

1. Установить фактический HEAD `main`, прочитать `PROJECT_STATE.md`, `ROADMAP.md`, `DECISIONS.md`, `CHECKPOINTS.md`.
2. Сверить `PROJECT_STATE.md` с текущим GitHub: коммиты, PR, статусы CI и развёртывания. При расхождении **зафиксировать его** и разрешить до новых изменений; запись о последней проверенной версии — это предыдущая контрольная точка, а не гарантия состояния HEAD.
3. Прочитать относящиеся к задаче разделы `INTEGRATION_COVERAGE.md`, `SOURCES_AUDIT.md`, `QA_REPORT.md`, `CHANGELOG.md`. Для содержания курса приоритет имеют шесть PDF НИУ ВШЭ, отсутствующих в публичном репозитории.
4. Выбрать конкретный ID задачи из `ROADMAP.md`. Если задача не описана, сначала добавить её и критерии готовности.
5. Создать рабочую ветку от проверенного HEAD `main`. Писать в `main` напрямую запрещено **правилом проекта**. Техническое принуждение требует правил защиты ветки на GitHub, которые проверяются отдельно.

## 2. Мелкие законченные этапы и контрольные точки

- Разбивать большие работы на самостоятельно проверяемые этапы: например, научная сверка презентации пачками слайдов, педагогическая проверка 5–10 учебных блоков, отдельная небольшая функциональная доработка.
- **После каждого этапа:** зафиксировать код/результат, выполнить доступные тесты, сделать коммит, обновить `PROJECT_STATE.md` и **добавить** запись в `CHECKPOINTS.md`. Указывать ID задачи, охват, фактические результаты и незакрытые вопросы.
- Для изменений интерфейса/поведения: дополнить регрессионные тесты, `CHANGELOG.md` и `QA_REPORT.md`; показать реальные PASS/FAIL, а не ожидаемые результаты.
- Работы в статусе IN_PROGRESS/BLOCKED не выдавать за завершённые. Не помечать выпуск как VERIFIED, пока нет фактического результата CI и (для публикации) Pages.
- Не переписывать историю ранее подтверждённых контрольных точек; последующие изменения добавлять ниже/выше отдельной записью.
- Разрешено делать несколько коммитов в рабочей ветке; `main` пополняется через PR после успешных проверок, по возможности объединением squash. Во время долгого этапа коммитить промежуточное состояние в **рабочую ветку**, ставить IN_PROGRESS и перечислять оставшееся. Не публиковать незавершённое как релиз.

## 3. Неизменные ограничения

- **Стабильная версия `v5.0.8/` не изменяется**. Хэш `v5.0.8/index.html` контролируется автоматически.
- Исходные 275 экзаменационных вопросов, включая 19 вопросов преподавателя, не менять без отдельного явно согласованного решения. Существующие идентификаторы ответов/ключи прогресса сохранять, обеспечить экспорт/импорт предыдущих версий.
- Приоритет шести презентаций НИУ ВШЭ; внешние источники/самостоятельные объяснения обозначаются корректно. Никакие закрытые PDF в публичный репозиторий не включать.
- Теория должна быть понятна новичку и продвигаться до продвинутого уровня. В каждом блоке пример обычной жизненной/практической ситуации, а у каждой формулы развёрнуты переменные, единицы, пример и условия применения.
- Естественный русский язык, выделение ключевых понятий, без неуклюжих калек и систематических риторических противопоставлений. Никаких формулировок о «фотографиях теста».
- Не ломать существующий ход экзамена, доступность, мобильный интерфейс, навигацию, источники и прогресс. Не объявлять 96/96 **академически проверенными** по одному лишь структурному тесту.

## 4. Минимальный релизный цикл

1. Рабочая ветка и запись `IN_PROGRESS` с ID задачи.
2. Независимая реализация + тесты + контрольная точка.
3. Обновить `PROJECT_STATE.md`, `CHECKPOINTS.md`, а при изменении приложения — `CHANGELOG.md`, `QA_REPORT.md`.
4. Открыть PR в `main`; дождаться зелёных jobs: проверка состояния, контент/регрессия, браузер.
5. После merge убедиться отдельно в зелёном GitHub Pages и совпадении live-версии с HEAD. Вести факты и ссылки. Если release/deploy ещё не проверены, ставить PENDING.
6. Повторное открытие новой задачи только после сохранения фактического состояния проекта. Не продолжать непроверенную ветку «по памяти».

## 5. Сбой / обрыв / переполнение чата

1. Прочитать пять документов из первого пункта и текущее состояние GitHub.
2. Найти последний VERIFIED checkpoint и последнюю рабочую ветку/открытый PR. Сравнить, какие коммиты **реально** существуют.
3. Проверить, что в рабочей ветке сохранено, а что осталось незакоммиченным/неполным. Незакоммиченную работу предыдущего чата считать **неподтверждённой и потенциально утраченной**.
4. Продолжать только недоделанные этапы задачи; повторно проверить затронутое, прежде чем объединять ветку.
5. Если CI красный, открытые вопросы или версия на сайте отличается — записать BLOCKED, причину и безопасное действие для восстановления.
6. Сообщать пользователю ссылки на доказательства: коммит/PR, CI, опубликованную версию, честно перечисляя ограничения.

## 6. Граница автоматической защиты

`tests/project-state-check.mjs` и GitHub Actions проверяют структуру документов, целостность замороженной версии и обязательные записи при PR с изменением кода. Эти проверки не сохраняют незакоммиченный текст внутри оборванного чата и не включают автоматически защиту ветки GitHub. Проверки Pages и научная редактура содержимого выполняются отдельно.


## 7. Чекпоинты только в Markdown-файлах (решение пользователя 25.10.2026)

- **Не выводить Markdown-чекпоинт в обычный текст ответа пользователю.** По запросу пользователя чекпоинты ведутся **только в файле**, прежде всего `CHAT_HANDOFF.md` (оперативное состояние) и `CHECKPOINTS.md` (журнал технических этапов).
- После каждого содержательного этапа и любого решения, меняющего план, обновить `CHAT_HANDOFF.md` через ветку/коммит; при кодовых доработках также актуализировать `PROJECT_STATE.md`, `ROADMAP.md` и исторический `CHECKPOINTS.md`.
- В файле указывать: версии, ветку/коммит, подтверждённые тесты и их ссылки, согласованные ограничения, выполненные и незавершённые действия и точный следующий шаг.
- В ответе пользователю давать обычный понятный отчёт и **ссылку на актуальный файл чекпоинта**, без вставки его текста в чат.
- При ограничении доступа к записи честно сообщить, что файл не обновлён. Неподтверждённые проверки не маркировать PASS.
